# MikroTik Firewall Architecture & Hardening

## Overview

A firewall is one of the most important security components of a network infrastructure.

This document demonstrates a structured approach to designing and hardening a MikroTik RouterOS firewall. The examples are intended for laboratory and educational use and should be adapted and tested before deployment in a production environment.

---

## 🎯 Objectives

The firewall design aims to:

* Protect the router itself
* Control traffic passing through the router
* Allow legitimate connections
* Block unwanted or malicious traffic
* Restrict administrative access
* Reduce attack surface
* Provide useful logging
* Establish a predictable security policy

---

# 🔥 RouterOS Firewall Architecture

MikroTik RouterOS primarily uses three firewall filter chains:

```text id="v6p5ca"
                  Incoming Packet
                        │
                        ▼
              ┌─────────────────┐
              │ RouterOS Firewall│
              └────────┬────────┘
                       │
          ┌────────────┼────────────┐
          │            │            │
          ▼            ▼            ▼
        INPUT        FORWARD       OUTPUT
          │            │            │
          ▼            ▼            ▼
       Router       Through       From Router
       itself       Router        itself
```

---

## 1. INPUT Chain

The `input` chain controls traffic destined for the router itself.

Examples:

* Winbox
* SSH
* Web management
* DNS service
* ICMP
* VPN termination
* Router services

Example:

```text id="9ec6n6"
Client ───────────────► MikroTik
                         │
                         ▼
                       INPUT
```

If an external host attempts to access the router's management interface, the packet is evaluated by the `input` chain.

---

## 2. FORWARD Chain

The `forward` chain controls traffic passing through the router.

Example:

```text id="c4g0jz"
LAN Client
    │
    ▼
MikroTik
    │
    ▼
Internet
```

The packet is not destined for the router itself. Therefore, it is evaluated by the `forward` chain.

Typical forward-chain policies include:

* LAN → Internet
* Guest → Internet
* Server → Internet
* Inter-network communication
* VPN → LAN
* WAN → Internal network

---

## 3. OUTPUT Chain

The `output` chain controls packets generated by the router itself.

Examples:

* DNS queries generated by the router
* NTP traffic
* Router-generated services
* Monitoring traffic
* Router-originated connections

Example:

```text id="u4t4cp"
MikroTik
    │
    ▼
  OUTPUT
    │
    ▼
Internet
```

---

# 🔄 Connection Tracking

RouterOS connection tracking maintains the state of network connections.

Common connection states include:

```text id="8g8nqu"
new
established
related
invalid
```

A typical secure firewall policy allows legitimate established and related connections while dropping invalid traffic.

Conceptually:

```text id="4g6cyx"
New Connection
      │
      ▼
Firewall Policy
      │
      ├── Allowed → Continue
      │
      └── Blocked → Drop
```

---

# ✅ Established & Related Connections

Allowing established and related connections early in the firewall can reduce unnecessary rule processing.

Conceptual rule:

```text
connection-state=established,related
action=accept
```

This commonly applies to both input and forward traffic, depending on the security policy.

---

# ❌ Invalid Traffic

Invalid connection states can indicate malformed, unexpected, or otherwise invalid traffic.

A common policy is:

```text
connection-state=invalid
action=drop
```

This should be tested carefully because firewall behavior depends on the network design and traffic patterns.

# 🔐 Protecting Router Management

Administrative interfaces should not be exposed unnecessarily.

Common RouterOS management services include:

```text
Winbox
SSH
HTTPS
HTTP
FTP
API
API-SSL
```

Only required services should remain enabled.

---

## Management Access Policy

A stronger design is to restrict administrative access to trusted networks.

Example:

```text id="5v93c1"
Trusted Management Network
          │
          ▼
      MikroTik
          │
          ├── Winbox → Allowed
          ├── SSH    → Allowed
          └── HTTPS  → Allowed

Internet
   │
   └── Management Access → Blocked
```

---

# 🛡️ Service Hardening

Unused RouterOS services should be disabled.

Examples of services that may be disabled when not required:

```text
FTP
Telnet
HTTP
API
API-SSL
```

The exact service list should be determined by operational requirements.

HTTPS, SSH, or Winbox can be retained where required and appropriately restricted.

---

# 🌐 WAN Protection

Traffic arriving from an untrusted WAN interface should be treated as untrusted.

A common security principle is:

```text id="x5r4bv"
WAN → Router
        │
        ├── Required service → Allow
        │
        └── Everything else → Drop
```

This follows a default-deny approach for unsolicited inbound traffic.

---

# 🔒 Forwarding Policy

Forward traffic should also follow the principle of least privilege.

Example policy:

```text id="i0m2xl"
LAN → Internet          ALLOW
Established/Related     ALLOW
VPN → Authorized LAN    ALLOW
Guest → Internet        ALLOW
Guest → Internal LAN    DENY
WAN → Internal LAN      DENY
Invalid Traffic        DROP
```

The exact policy depends on the network architecture and business requirements.

---

# 🚫 Blocking Unauthorized WAN Access

A router should not allow unsolicited WAN traffic to internal systems unless there is a deliberate requirement.

For example:

```text id="2d9e5h"
Internet
    │
    ▼
WAN Interface
    │
    ▼
Firewall
    │
    ├── Required Port → Controlled Access
    │
    └── Unknown Traffic → DROP
```

Port forwarding should only be implemented when necessary and should be protected with additional controls where possible.

---

# 🧱 Default-Deny Principle

A strong firewall architecture generally follows:

```text id="2v2yps"
ALLOW
  ↓
Required Traffic
  ↓
DROP
  ↓
Everything Else
```

Instead of trying to identify every possible malicious connection, the firewall can define what is explicitly allowed and deny traffic that does not meet the policy.

---

# 🧑‍💻 ICMP

ICMP is useful for:

* Troubleshooting
* Network monitoring
* Path MTU discovery
* Connectivity testing

Therefore, completely blocking ICMP is not always appropriate.

A better approach is to allow required ICMP traffic while controlling unnecessary or abusive traffic according to the environment.

---

# 🔎 DNS Security

If the MikroTik router provides DNS services, DNS access should be carefully controlled.

Potential policy:

```text
Trusted LAN → Router DNS → ALLOW
Internet → Router DNS → RESTRICT
```

Open recursive DNS services should not be unintentionally exposed to the Internet.

---

# 🚨 Brute-Force Protection

Administrative services such as SSH and Winbox may be targeted by automated login attempts.

Possible defensive measures include:

* Restricting management access to trusted IP ranges
* Using strong credentials
* Disabling unnecessary services
* Changing exposed management ports where appropriate
* Using address lists
* Rate limiting suspicious connections
* Monitoring logs
* Using VPN-based administration

Changing the port alone should not be considered a complete security control.

---

# 📋 Address Lists

RouterOS address lists can simplify firewall policy management.

Example conceptual structure:

```text id="9psa5q"
TRUSTED-MANAGEMENT
    │
    ├── Admin Network
    ├── IT Workstation
    └── VPN Management Network
```

Firewall rules can then reference the address list instead of maintaining many individual rules.

---

# 📝 Logging

Firewall logging can help during:

* Troubleshooting
* Security investigations
* Incident response
* Traffic analysis

However, excessive logging can create unnecessary load and large log volumes.

A practical strategy is to log important events rather than every packet.

Examples:

```text id="1r74hb"
Blocked WAN access
Authentication attempts
Critical firewall drops
VPN events
Configuration changes
```

---

# 🔍 Troubleshooting Workflow

When a firewall blocks legitimate traffic:

```text id="8u9f3c"
Identify Source
      ↓
Identify Destination
      ↓
Identify Protocol / Port
      ↓
Check Connection State
      ↓
Check Firewall Chain
      ↓
Check Matching Rule
      ↓
Review Logs
      ↓
Test
      ↓
Document
```

Useful checks may include:

* Firewall rule counters
* Connection tracking
* Logs
* Torch
* Packet capture
* Routing table
* NAT rules

# 🧪 Example Security Policy

A generalized secure policy might follow this structure:

```text id="y0t6ku"
1. Accept established / related traffic
2. Drop invalid traffic
3. Allow required management access
4. Allow required VPN traffic
5. Allow required LAN services
6. Restrict WAN access to the router
7. Restrict unauthorized forwarding
8. Log important denied traffic
9. Drop remaining unwanted traffic
```

Rule ordering is important because RouterOS evaluates firewall rules sequentially.

---

# 🔐 Security Principles

The firewall design follows several fundamental security principles:

### Least Privilege

Allow only the traffic that is required.

### Default Deny

Unmatched or unauthorized traffic should not be trusted automatically.

### Defense in Depth

Firewall rules should work together with:

* Strong authentication
* VPN
* System hardening
* Monitoring
* Secure backups
* Access control

### Minimize Attack Surface

Disable unnecessary services and restrict management interfaces.

### Monitor and Review

Firewall configurations should be reviewed periodically.

# 🧭 Recommended Management Architecture

For sensitive infrastructure, administrative access can be routed through a VPN.

```text id="o8skp1"
Administrator
      │
      ▼
   VPN / WireGuard
      │
      ▼
Management Network
      │
      ▼
   MikroTik
      │
      ├── Switches
      ├── Servers
      ├── APs
      └── Other Infrastructure
```

This reduces the need to expose management services directly to the public Internet.

## 📝 Key Takeaways

A good MikroTik firewall should:

* Protect the router itself
* Control forwarded traffic
* Restrict management access
* Follow least-privilege principles
* Use connection tracking appropriately
* Avoid unnecessary exposed services
* Log important security events
* Be documented and regularly reviewed

Firewall configuration is not a one-time task. It should evolve with the network, applications, security requirements, and operational needs.
